# Контейнеры и взаимодействия

Схемы — C2: приложения и хранилища. Число экземпляров и размещение показаны отдельно в [ADR 001](../ADR/001-architecture-variants.md).

## Стек нового решения

Фронтенд локального терминала и панели самообслуживания — **микрофронтенды React + Vite** по [ADR 007](../ADR/007-microfrontends.md): оболочка, инциденты, оборудование, аналитика и управление SaaS. На ферме локально доступны оболочка, инциденты и оборудование; обновления активируются только полным совместимым комплектом с откатом. Бэкенд — **C#/.NET**: ASP.NET Core для API, .NET Worker для фоновых процессов и локального агента терминала. Агент принимает тревоги от локального оповещения, хранит полученные карточки независимо от браузера. В варианте Б таймеры эскалации ведёт сервис инцидентов. Существующие React/Flutter-клиенты сохраняются, но требуют адаптации к API AgroWatch. Для местных мобильных уведомлений добавляется WSS-подключение по ЛВС; фоновая доставка и восстановление соединения проверяются на управляемом устройстве дежурного. Полная замена приложений не требуется.

Выбор C#/.NET учитывает опыт разработчика с этим стеком: это уменьшает объём освоения нового языка и инструментов при реализации MVP. Совместимость видеоконвейера и партнёрской модели проверяется отдельно.

Видеоаналитика также имеет C#-обвязку. [ONNX Runtime предоставляет C# API](https://onnxruntime.ai/docs/get-started/with-csharp.html), но формат партнёрской модели пока неизвестен: ONNX/нативный SDK — кандидат, совместимость, качество и GPU-бюджет проверяются до реализации. Формат модели не меняем без проверки поставщика. Kafka, PostgreSQL и клиентские системы сохраняют свои технологии.

## Вариант А: локальный сервер

![C2 варианта А](diagrams/c2-a-alternative.svg)

[PNG](diagrams/c2-a-alternative.png) · [PlantUML](diagrams/c2-a-alternative.puml)

Видеоаналитика посылает срочную тревогу напрямую в оба локальных получателя. Приложение фермы объединяет инциденты и учёт; транзакция PostgreSQL фиксирует факт и outbox. Синхронизация читает outbox независимо от оповещения.

## Вариант Б: распределённая обработка

![C2 варианта Б](diagrams/c2-b-primary.svg)

[PNG](diagrams/c2-b-primary.png) · [PlantUML](diagrams/c2-b-primary.puml)

Видеоаналитика на пяти узлах публикует наблюдения в Kafka из устойчивого буфера. Сервис оповещения читает их сразу, независимо от сервиса инцидентов и ИИ. Отдельные consumer groups доставляют терминалу и сирене: сбой одного получателя не блокирует другого. Сервис инцидентов хранит основное состояние карточки и связывает её подрепорты. При недоступной Kafka новые тревоги ожидают доставки; ранее полученные карточки видимы. Принятие/закрытие подтверждается доменным фактом, а не HTTP 202.

### Состояние инцидентов

Для обработки событий в C# выбран **Streamiz.Kafka.Net**, знакомый Святославу по проекту клиники. Состояние окон, карточек и дедупликации хранится во встроенном RocksDB на постоянном томе; изменения резервируются в Kafka changelog с RF=4/minISR=2. Это не отдельный сервер RocksDB и не новая JVM-служба. SQL-представления для чтения и учёта остаются отдельным производным слоем; сирена их не ждёт.

Экземпляры обработки работают на E1/E2/E3; каждой партицией владеет один активный обработчик. После отказа задача назначается живому экземпляру, использует сохранившееся местное состояние и дочитывает журнал изменений, либо восстанавливает его на другом узле. Постоянный том не является репликой сам по себе. Готовые standby replicas в текущей таблице возможностей Streamiz не поддерживаются: мгновенное переключение на прогретую копию RocksDB не обещается. Пока состояние не готово, обработка карточки не выдаётся за успешную; независимое оповещение продолжает работу при доступной Kafka.

Опыт клиники обосновывает знакомый инструмент, но не подтверждает нагрузку или время восстановления на ферме. На пилоте фиксируют версию пакета, проверяют persistent store/changelog, обработку повторов, транзакции, rebalance и время возвращения карточек. [Возможности Streamiz](https://github.com/LGouellec/streamiz#compare-kafka-streams-vs-streamiz) проверены 29.09.2026.

### Доступность SQL-представлений

В Б PostgreSQL хранит производные карточки, учёт и справочники: основной экземпляр на E1, асинхронные реплики на E3 и E5. Это процессы на существующих edge-узлах, не дополнительные центральные серверы. Их CPU, RAM, диск и трафик репликации входят в нагрузку пилота. Репликация PostgreSQL независима от RocksDB/changelog Streamiz.

При отказе E1 выбирают наиболее свежую доступную копию, исключают запись прежним основным экземпляром и переключают адрес БД. Если прежний экземпляр нельзя надёжно отключить от записи, переключение не выполняют. Применённые позиции событий хранятся в одной SQL-транзакции с представлением; после переключения обработчик дочитывает Kafka с этих позиций и подавляет повторы. Так восполняется отставший хвост, пока он доступен в журнале. Резервные копии нужны отдельно от реплик. [Репликация PostgreSQL](https://www.postgresql.org/docs/current/warm-standby.html) и [условия переключения](https://www.postgresql.org/docs/current/warm-standby-failover.html).

Пока чтение не восстановлено, API явно сообщает о недоступности полного представления; терминал показывает сохранённые карточки с отметкой свежести и продолжает получать новые тревоги. Доменные команды через доступную Kafka не зависят от SQL-проекции, но успех показывается только после подтверждения доменом; операции, которым нужны недоступные справочники, отклоняются. Учебная цель возвращения актуального чтения после одного отказа — до 5 минут, подлежит проверке. Это не обещание пятисекундного восстановления всех экранов или нулевой потери данных при любом отказе.

## Управление оборудованием и учёт

![Оборудование и учёт — Б](diagrams/c2-equipment.svg)

[PNG](diagrams/c2-equipment.png) · [PlantUML](diagrams/c2-equipment.puml)

![Оборудование и учёт — А](diagrams/c2-equipment-a.svg)

[PNG](diagrams/c2-equipment-a.png) · [PlantUML](diagrams/c2-equipment-a.puml).

В А API, инциденты, оборудование и учёт — модули Приложения фермы; шлюз — отдельный процесс. В Б это сервисы на том же edge-пуле. Подробности допуска и fencing в [Task3](../Task3/README.md).

**Фильтрация воды (F04).** Шлюз передаёт показания и время измерения. В Б сервис «Управление оборудованием» сравнивает их с локально сохранёнными порогами и проверяет давность последнего показания. При отклонении или потере телеметрии публикует наблюдение с ID оборудования и причиной в Kafka; его читают оповещение и инциденты. Нормальное показание само по себе тревогу не создаёт. В А эти же правила выполняет модуль оборудования Приложения фермы: фиксирует случай в SQL/outbox и отправляет местную тревогу напрямую. Ни ИИ, ни интернет для этого не нужны; пороги задаются по спецификации оборудования.

**Поголовье и корм (F05–F06).** Три обработки камеры не складываются в три подсчёта: учёт выбирает один актуальный результат назначенного источника для зоны и периода, хранит его качество и допускает ручную корректировку с причиной. Уникальность животных между зонами не считается доказанной распознаванием. Остаток корма меняется по подтверждённым фактам прихода и фактической выдачи, а не по отправленной команде. Центр строит прогноз по истории расхода, подтверждённому поголовью и плану кормления; при отсутствии свежей синхронизации показывает давность исходных данных.

## Центральная часть

![C2 центральной части](diagrams/c2-center.svg)

[PNG](diagrams/c2-center.png) · [PlantUML](diagrams/c2-center.puml)

В пилоте центральная Kafka принадлежит существующей платформе данных AgroTech X и показана за границей AgroWatch. Продукту выделены топики, учётные записи и квоты; схемами событий и потребителями владеет команда AgroWatch, эксплуатацией брокеров — команда платформы. Ферменные кластеры входят в AgroWatch. Переход к инфраструктуре оператора SaaS описан в [ADR 004](../ADR/004-saas-isolation.md).

MM2 развёрнут в центре и читает доступные ферменные брокеры через защищённую сеть. Для варианта А шлюз принимает HTTPS-пакеты outbox и подтверждает после устойчивой записи. API и потребители используют общий проверяемый модуль tenant-маршрутизации, но каждый сервис сохраняет владение своими данными. Блок БД клиентов — логическая совокупность БД в периметре сервисов, не разрешение всем сервисам писать любые таблицы.

ИИ получает факты и ссылки на медиа; рекомендация публикуется через API отдельным фактом и доезжает вниз. Базовые инциденты не зависят от ИИ. Версии политик и отзывов доставляются как данные, JWKS кэшируются API; собственно проверка подписи и разрешений локальна.

## Политики, намерения и эскалация

В Б выбран один путь вниз: центральный API → центральная Kafka → MM2 в центре → allowlist-топики локальной Kafka → агент политик и медиа → локальный API → топик команды Kafka → нужный домен. Прямого центрального допуска оборудования нет. HTTPS агента к центру используется для файлов медиа/моделей; права и команды получают через топики. В А тот же шлюз синхронизации обменивается outbox и входящими данными по HTTPS, затем вызывает локальное приложение.

В Б оповещение потребляет наблюдения и команды эскалации из Kafka; таймеры сервиса инцидентов публикуют эскалацию в тот же локальный кластер. Состояние таймеров восстанавливается из журнала. При недоступном кластере новые сигналы и эскалация задерживаются; уже активный сигнал не исчезает. В А таймеры остаются в агенте терминала. [Ограничения каналов и сроки](../appendix/local-control-and-offline-access.md).

Поставщик модели загружает подписанную версию в центральный реестр артефактов (часть медиасервиса). Агент скачивает пакет по HTTPS, проверяет подпись и совместимость, развёртывает по одной копии камеры с rollback. Контроллер развёртывания работает в центре; действующее назначение кэшировано на ферме и без WAN не исчезает.

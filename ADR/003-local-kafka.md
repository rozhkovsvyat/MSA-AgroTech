# ADR 003 — локальная Kafka и обмен с центром

Автор: Святослав Рожков. Дата: 28.09.2026.

Статус: Принято.

Вклад ИИ в подготовку: [AI-log](../AI-LOG.md).

## Функциональные требования

| № | Участники | Сценарий | Порядок действий |
|---|---|---|---|
| F01 | Видеоаналитика, оповещение | Доставить первое обнаружение | 1. Записать наблюдение в локальную Kafka. 2. Прочитать его обработчиками терминала и сирены. 3. Зафиксировать результат каждого канала и повторить незавершённую доставку. |
| F03 | API, сервис оборудования, шлюз | Передать команду до исполнителя | 1. Проверить запрос. 2. Записать команду в Kafka. 3. Проверить допуск на ферме. 4. Выполнить действие и отдельно записать результат. |
| F07 | Ферма, центральная аналитика | Передать историю в центр | 1. Сохранить события на ферме. 2. При доступной связи скопировать их в центр. 3. Построить отчёты, не считая повторы новыми событиями. |

## Решение

В выбранном варианте Б прикладные события и межсервисные команды проходят через локальную Kafka. Путь тревоги: видеоаналитика → Kafka → сервис оповещения → терминал и сирена. Обработчик начинает доставку по первому наблюдению: без ожидания второй модели, ИИ, основной карточки инцидента или окончания окна 60 с. Обходной путь от распознавателя к получателям не используется.

На пяти вычислителях размещены пять брокеров и пять KRaft-контроллеров. Для критичных и служебных топиков выбраны **RF=4, min.insync.replicas=2, acks=all**, идемпотентный producer и запрет unclean election. Четыре реплики каждой партиции размещаются на четырёх разных физических устройствах; назначения балансируются по пяти брокерам. Для позиций и транзакций также задаются `offsets.topic.replication.factor=4`, minISR=2 у `__consumer_offsets`, `transaction.state.log.replication.factor=4`, `transaction.state.log.min.isr=2`. Журналы состояния и промежуточные топики Streamiz получают ту же политику. Проверяется фактическая конфигурация уже созданных топиков.

Число вычислителей, контроллеров и копий данных решает разные задачи:

| Параметр | Основание |
|---|---|
| Пять вычислителей | 16 камер × три обработки = 48 задач при ёмкости 10 на устройство. Каждая камера назначается трём разным устройствам. |
| Пять контроллеров | Большинство из трёх сохраняет управление Kafka при любых двух отказах. Три контроллера выдержали бы только один. Они управляют метаданными, а не голосуют за каждую запись наблюдения. |
| Четыре копии партиции | После двух отказов из полностью синхронного состояния остаются минимум две копии для записи. Пятая копия дала бы дополнительный запас, но потребовала бы больше диска и трафика. |
| Минимум две синхронные копии | Продолжаем принимать тревоги при двух актуальных копиях. Значение 3 остановило бы запись в таком состоянии. Принимаем меньший запас сохранности ради доступности тревоги. |

ISR — копии, успевшие синхронизироваться. `acks=all` ждёт все текущие ISR, а не всегда ровно две. Снижение minISR не ускоряет запись при полном ISR; влияние RF на задержку измеряется. Два оставшихся контроллера из пяти не имеют большинства: они не могут безопасно отличить отказ остальных от разрыва сети.

Сервис оповещения развёрнут на E1/E3/E5. Терминал и сирена используют отдельные consumer groups: недоступный терминал не удерживает позицию сирены. Получатели принимают команды желаемого состояния с ID и версией. При неизвестном результате команда повторяется с паузами в пределах срока и числа попыток; исчерпание показывает неподтверждённое исполнение. Повтор не перезапускает уже включённую тревогу, старая версия не отменяет более новое выключение. ACK Kafka означает запись, ответ контроллера — применение команды программой, но не доказательство физического звука. [Контракт оповещения](../appendix/incident-event-contract.md).

Локальный API принимает HTTP-команду, проверяет доступ и публикует её в топик домена. HTTP 202 означает постановку, результат показывает отдельный доменный факт. Команды оборудования проходят локальный допуск; шлюз читает разрешённые команды из Kafka и повторно проверяет срок, epoch и ID перед физическим действием. Видео идёт по RTSP, чтение карточек — через API, файлы — по HTTPS/S3; эти потоки в Kafka не переносятся.

MirrorMaker 2 работает в центре. Факты идут вверх, политики/намерения/рекомендации — вниз по отдельным allowlist-топикам без циклической репликации. Обрыв WAN не останавливает локальный путь.

## Альтернативы

Прямое оповещение с независимой записью истории уменьшает зависимость от брокера, но требует двух согласованных путей доставки и состояния повторов. Выбран единый путь для упрощения реализации. Вариант А остаётся рассмотренной альтернативой с одним сервером, прямым оповещением и SQL/outbox. Одиночные журналы не защищают непереданную историю при потере диска; растянутый через WAN кластер нарушает автономность фермы.

RF=3/minISR=2 недостаточно для записи после любой пары отказов. RF=4/minISR=2 удовлетворяет этой модели при исходно полном ISR. RF=5/minISR=2 сохраняет ещё одну актуальную копию в худшем случае, но этот запас не выбран: четыре копии требуют на 20% меньше места для реплик, чем пять. Это не экономия 20% всего оборудования и не измеренное ускорение. minISR=3 лучше защищает новые подтверждённые записи, но раньше останавливает тревоги.

## Недостатки, ограничения, риски

После любых двух отказов из исходных четырёх синхронных реплик партиции остаются минимум две; из пяти контроллеров — три. Выбор лидера и переназначение потребителей дают паузу. Если реплика отстала ещё до отказов, записи может не быть. При ISR<2 или недоступном кластере новые тревоги задерживаются: локальный буфер ожидает доставки, персонал переходит к ручному реагированию, новые автоматические физические допуски запрещены. Прямой обход Kafka не вводится.

Подтверждённое в деградации событие может находиться только на двух устройствах. Последующая потеря обеих этих копий может уничтожить его; RF=4 не означает, что каждая новая запись всегда уже есть на четырёх носителях. Сохранность ранее подтверждённых событий и доступность новых записей проверяются отдельно.

После простоя оповещение включено по умолчанию. Уполномоченный сотрудник может до возобновления очереди явно подавить звук для событий за выбранный период простоя; события сохраняются, свежие случаи вне периода оповещаются. Историческое построение представлений само не управляет сиреной. Возраст не доказывает устранение опасности: неизвестные исходы остаются видимыми. [Правила после простоя](../appendix/incident-event-contract.md).

Цена решения — четырёхкратное хранение критичных журналов, сеть и конкуренция с распознаванием. Совмещение брокеров и контроллеров — компромисс небольшого локального пула: у них общие CPU, диск и отказ устройства. Это не рекомендуемая Apache Kafka изоляция для критичных развёртываний; отдельные роли/ресурсы — вариант пересмотра при провале пилота. Десять обработок на узел должны сохраняться с этим резервом. Пять секунд проверяются от появления опасности до сигнала, включая выбор лидера, повтор и получателя. Испытания кластера не выполнены; [расчёт и контрпримеры](../appendix/local-kafka-decision-review.md) не заменяют измерений.

## Итог выбора

Для автономной фермы выбираем локальную Kafka с четырьмя копиями данных, минимум двумя синхронными и пятью контроллерами вместо отдельных журналов. Получаем общий путь событий и запись после двух отказов из полностью синхронного состояния; принимаем остановку тревог при недоступном журнале и меньший запас сохранности новых записей в деградации.

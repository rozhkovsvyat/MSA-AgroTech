# ADR 004 — изоляция SaaS по базе данных клиента

Автор: Святослав Рожков. Дата: 28.09.2026.

Статус: архитектурный выбор согласован; редакция документа подготовлена для итогового ревью автора. Подробности реализации ниже — проект, а не отчёт о внедрении.

## Функциональные требования

| № | Участники | Use Case | Шаги |
|---|---|---|---|
| F08–F09 | Клиент, платформа | Подключить компанию | Создать tenant → права → БД → фермы → кабинет |
| S01 / Task5 | Клиент, биллинг | Оплатить использование | Выбрать тариф → собрать usage → выставить счёт → сверить платёж |

## Нефункциональные требования

| № | Требование |
|---|---|
| R01 / P01 | Локальная работа без WAN; тревога ≤ 5 с от возникновения ситуации |
| P02 / R02 | Синхронизация ≤ 10 мин при связи; целевая доступность 99,95% |
| C01–C05 | Один центральный сервер максимум плюс edge; готовая ML-модель; разные камеры, нестабильная сеть и ошибки распознавания |

Номер ADR 004 сохраняет порядок исходного решения об изоляции; эта редакция для Task5 дополняет его ссылкой на последующее сравнение ADR 005.

## Контекст

SaaS развивает выбранный в [ADR 005](005-architecture-choice.md) вариант Б. Tenant — компания с несколькими фермами. Предполагаем десятки крупных клиентов на раннем этапе; это гипотеза, не данность задания.

## Альтернативы

| Модель | Выигрыш | Цена и ограничения |
|---|---|---|
| Схема на клиента в общей БД | Одна инсталляция БД, меньше соединений/инфраструктуры | Раздельные роли и schema qualification обязательны; ошибочный search_path/GRANT может нарушить изоляцию; backup/PITR обычно общий |
| БД на клиента, общее приложение | Независимая роль/экспорт/перенос клиента; легче разнести ресурсы | Миграции и копии по N базам; лимиты соединений; общий сервер всё ещё общий домен отказа |
| Отдельный экземпляр приложения и БД | Изоляция вычислений и релизов, независимые квоты | N deployments и обновлений, высокая цена маленького клиента |

Общие таблицы с tenant_id — другая модель; она не подменяет схему на клиента. Выделенный экземпляр даёт реальные дополнительные свойства и остаётся корпоративной опцией.

## Решение

Выбрана **БД на клиента при общем приложении**. Реестр размещения и общая библиотека выбирают подключение только из проверенного tenant-контекста. Роли БД ограничены соответствующим клиентом. Принцип применяется в периметре каждого сервиса: биллинг владеет своими таблицами, доменные сервисы — своими; общей схемы для произвольной записи всеми сервисами нет.

## Недостатки, ограничения, риски

Резолвер не единственный возможный источник утечки: проверяются API, event envelope, кэш, объектные ключи и выдаваемые ссылки. Нужны негативные тесты tenant A → tenant B для каждого пути. PostgreSQL PITR на общем кластере требует отдельной процедуры: восстановить копию кластера, извлечь нужную БД, перенести клиента; не обещаем мгновенный независимый PITR.

Provisioning, миграции, резервные копии, учёт версий и офбординг автоматизированы по проекту. Без этих механизмов эксплуатационная цена растёт. [Схемы моделей и To-Be](../Task5/README.md), [коммерческий контур](../Task5/saas-commercial.md).

Дежурный работает через локальный терминал даже при потере WAN. Центральный кабинет нужен для отчётов и администрирования компании. Одной БД клиента недостаточно для изоляции: проверяется tenant на всех каналах и в медиа.

## Трассировка

Task5: три модели — первые три C2; итоговые C1/C2 — далее; AgroTech X с фермами — последний вид. Подписки, российский провайдер, scope, dev-портал, самообслуживание, масштабирование и usage — [коммерческая модель](../Task5/saas-commercial.md). F07–F09, R01, P02, S01 покрываются этими контрактами; фактические SLO проверяются при реализации.

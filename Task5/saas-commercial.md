# Коммерческая модель и эксплуатация SaaS

## Подписки

| Тариф | Возможности | Единица |
|---|---|---|
| Пилот | 1–3 фермы, базовые отчёты | Ферма / месяц |
| Производственный | Пользовательские метрики, API, ИИ-триаж | Ферма + сверхлимитное использование |
| Корпоративный | Выделенные ресурсы или экземпляр, договорный SLA | Индивидуальный расчёт |

Цены не назначены: нужны данные затрат. Тариф не выключает локальную защиту животных. Неоплата ограничивает новые подключения и облачные квоты после предупреждения; офбординг включает экспорт и подтверждённое удаление по регламенту.

## Usage, биллинг и платёж

Центральная Kafka несёт usage с tenant_id, farm_id, event_id, единицей, периодом и версией тарифа. Биллинг подавляет повторы по event_id и ведёт свой журнал счетов. Счёт содержит снимок тарифа; поздние события после WAN-обрыва дают корректировку, не второе списание за тот же факт. Метрики: активные фермы/камеры, API-вызовы, объём медиа, ресурсы ИИ. Пользовательские производственные метрики хранят единицы, формулу и версию отдельно от платёжных.

Учебный выбор российского провайдера — **ЮKassa**. Создание платежа имеет idempotency key; timeout не означает неуспех. Webhook служит сигналом проверить состояние платежа по API; повтор не создаёт новый платёж. Секреты и платёжные данные не хранятся в клиентском интерфейсе. Возможность конкретного договора и автоплатежей проверяют при внедрении. [Документация платежей](https://yookassa.ru/developers/api#create_payment).

## API и самообслуживание

Scope: `incidents:read`, `metrics:read`, `media:read`, `equipment:request`. Tenant и farm берутся из проверенного контекста; команда всё равно проходит локальный допуск. JWT имеет короткий TTL; центральный denylist/версия прав ускоряет отзыв, при отсутствии проверки отзыв действует по сроку токена. На ферме — срок офлайн-прав, без обещания мгновенного отзыва через оборванный WAN.

Dev-портал содержит OpenAPI, примеры, журнал версий, sandbox с тестовым tenant, выдачу/ротацию client credentials. Панель самообслуживания: организация, пользователи, фермы, тариф, счета, usage и экспорт. Отдельная панель администратора платформы не вводится; служебные операции идут через регламентированные jobs и API.

## Масштабирование и изоляция

API и workers масштабируются горизонтально; партиции выбираются по tenant/farm/агрегату с контролем горячих ключей. БД распределяются по серверам через реестр; перенос включает копию, догоняющую синхронизацию, переключение версии реестра и проверку. Quotas, connection pools и лимиты фоновых задач сдерживают noisy neighbor. Kafka ACL, media-prefix и API проверяются независимо от БД. Фермы автономны, добавление новой не требует релиза остальных.

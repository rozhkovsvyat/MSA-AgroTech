# Контракт инцидента

Инцидент — вызов в зону и набор подрепортов об одной или нескольких опасностях. Первое обнаружение немедленно публикуется в Kafka; оповещение читает его без ожидания подтверждения другой модели. При исправном кластере доставка начинается сразу; при отказе Kafka новое наблюдение ожидает доставки. Три обработчика одного видео нужны для непрерывности, не для голосования и не для определения числа животных.

Группировка: zone_id и интервал **60 секунд от occurred_at первого наблюдения**; окно не скользит при каждом дополнении. Терминал начинает по первому полученному сигналу. Сервис инцидентов хранит окончательное соответствие подрепортов инцидентам; часы синхронизируются, source time и receive time сохраняются. При недостоверном времени/зоне не склеиваем автоматически. Это проектное уточнение механизма, а не измеренная точность корреляции.

Поздний подрепорт добавляется автоматически только по однозначному идентификатору существующего эпизода. Без него создаётся отдельная карточка. ИИ может предложить связь с основаниями, но объединение подтверждает сотрудник; отказ или задержка агента не задерживают тревогу. Попадание в окно не означает одного животного: все места/кадры остаются видимыми. Новая опасность после закрытия не подавляется как повтор; история известного ID не вызывает старую тревогу заново.

События: ObservationRecorded, IncidentOpened, SubreportAdded, AlertDelivered, IncidentAccepted, ResponsibilityTransferred, AiRecommendationAppended, IncidentClosed. У каждого event_id, tenant_id, farm_id, zone_id, occurred_at, received_at, schema_version; команды имеют idempotency key и expected_version.

Один исполнитель по карточке после принятия; передача завершается только после подтверждения новым. Это отметка «занимаюсь этим случаем», а не установление трудовой или юридической ответственности сотрудника. Эскалация не снимает текущего исполнителя. ACK сирены не означает, что сотрудник занялся конкретной карточкой. Критичный исход закрывает человек. Закрытие ИИ возможно только при включённой политике для разрешённых случаев низкого риска; связанные опасности не закрывает. [Режимы и ограничения](ai-risk-autonomy.md).

ИИ анализирует асинхронно и добавляет рекомендацию отдельно, сохраняя наблюдения. Сбой ИИ не блокирует карточку; несрочный инцидент сотрудник может прочитать после анализа, срочный требует сразу идти на место.

[Пороги и права](local-control-and-offline-access.md). Replay журнала обновляет представление без повторного физического действия. Проекция не подтверждает исполнение оборудования.

Сигнализация ведёт активную тревогу по зоне: новые подрепорты дополняют её причины, а не обозначают число животных. Снятие звука не принимает и не закрывает инцидент; новая подтверждённо отдельная опасность подаёт сигнал снова. Дедупликация observation_id защищает от транспортного повтора, но не обещает физическое exactly-once после потери подтверждения или перезапуска получателя.

В Б оповещение и инциденты — независимые потребители наблюдений. Результаты каждого канала фиксируются с observation_id и receiver_id; consumer offset не подтверждается как успешно доставленный до устойчивой фиксации результата/задания повтора. Сбой после физического сигнала до фиксации результата допускает повтор; дедупликация получателя снижает его. После восстановления доставка учитывает актуальное состояние команды и явное подавление за период простоя; историческая пересборка проекций не вызывает получателей.

## Ручная карточка

Сотрудник может создать инцидент с зоной, описанием и временем фактического происшествия. Система отдельно сохраняет время внесения и пользователя. В форме есть явный выбор: **«Оповестить»** (включён для нового текущего случая) или **«Только журнал»**. Второй режим нужен для уже оказанной помощи, записи после простоя и случая, которым сотрудник уже занимается. Режим записи и состояние карточки независимы: отсутствие звука не означает закрытия; для закрытия нужен исход.

В варианте Б команда из терминала проходит через локальный API и Kafka в сервис инцидентов. Сервис проверяет права и повтор команды, создаёт карточку с `source=manual`; только при выборе «Оповестить» публикует `AlertRequested` с устойчивым ID. Сервис оповещения читает этот запрос из Kafka и запускает обычные каналы терминала и сирены. «Только журнал» не создаёт запрос тревоги или автоматические повторные вызовы по этой записи. Сотрудник может позднее явно запросить оповещение.

При недоступной Kafka ручное реагирование выполняется вне системы по регламенту фермы. Неподтверждённая запись в интерфейсе не считается сохранённым инцидентом. После восстановления сотрудник переносит записи о прошедших случаях в режиме «Только журнал». Это не обход Kafka для звукового оповещения.

## Возобновление после простоя

По умолчанию задержанное новое наблюдение оповещается; `occurred_at` остаётся временем обнаружения, `received_at` показывает задержку. Если персонал уже реагировал вручную, уполномоченный сотрудник до возобновления очереди включает «Не озвучивать события за период простоя» и выбирает ферму/зоны и интервал времени обнаружения. Записываются пользователь, причина и версия правила. Правило подтверждается системой до продолжения очереди; при его неподтверждённом состоянии подавление не обещается.

Подавление касается звука и повторных звуковых эскалаций по выбранным событиям. Карточки, наблюдения и неизвестные исходы остаются видимыми. Свежие обнаружения вне интервала оповещаются, даже если связаны с той же карточкой. При недостоверном времени подавление автоматически не применяется. Уже включённый звук выключается отдельным действием; режим не означает закрытия инцидента. Историческая пересборка состояния не считается новой доставкой и сама не инициирует звук.

## Команда сирене

Передаётся желаемое состояние с `alert_id`, `receiver_id`, `version`, `desired_state` и сроком действия. Версия растёт для одной тревоги: повтор той же версии возвращает прежний результат, старая версия не включает звук после нового выключения. Пока есть другая активная причина, выключение одной тревоги не гасит общий сигнал зоны.

Контроллер устойчиво сохраняет принятое состояние, применяет его к выходу и отвечает. После своего перезапуска сверяет выход с сохранённым состоянием. При потере ответа отправитель повторяет ту же команду с паузой и ограничением по сроку и числу попыток. Исчерпание даёт статус «Выполнение не подтверждено»; независимая доставка терминалу продолжается. Значения таймаутов и числа попыток определяются на пилоте в бюджете реакции.

Повтор нужен при временной потере связи, перезапуске получателя или потерянном ответе. Он не ремонтирует сирену. Подтверждение контроллера означает применение программой, а не измерение физического звука. Kafka exactly-once не охватывает этот внешний эффект: используем повторную доставку и безопасное применение состояния. Нельзя просто подтвердить Kafka-позицию до устойчивой фиксации задания и потерять команду при сбое.
